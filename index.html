Исследование влияния ReDoS на производительность веб-приложений

Цель работы — исследовать зависимость времени выполнения регулярных выражений от длины входной строки и оценить влияние избыточного перебора на отзывчивость интерфейса. В работе сравниваются выражения, уязвимые к ReDoS (Regular expression Denial of Service), и их оптимизированные варианты.

ReDoS возникает, когда обработка специально сформированной строки требует большого числа возвратов при поиске совпадения (backtracking). Для рассматриваемых выражений рост затрат может быть экспоненциальным или полиномиальным. Практическую значимость проблемы иллюстрируют инциденты Stack Overflow в 2016 году1 и Cloudflare в 2019 году2. 

// один и тот же вход: "aaaa…a!"
/^(a+)+$/.test(input)   // O(2^n) — небезопасно
/^a+$/.test(input)      // O(n)   — безопасно

1. Сравнение времени выполнения

Для выбранной пары выполняется проверка одной и той же входной строки. Обозначение unsafe соответствует уязвимому выражению, safe — оптимизированному варианту. Вычисления выполняются в отдельных Web Worker. При превышении заданного времени ожидания воркер завершается принудительно.

2. Зависимость времени выполнения от длины входа

Измерения проводятся для последовательности возрастающих длин входа. Для каждой длины определяется медиана времени выполнения. Оптимизированное выражение дополнительно проверяется на более длинных строках. Обе оси графика имеют логарифмическую шкалу. Превышение времени ожидания обозначается крестиком. После первого таймаута последующие измерения уязвимого выражения пропускаются.

3. Влияние вычислений на отзывчивость интерфейса

Эксперимент сравнивает выполнение уязвимого выражения в основном потоке страницы и в Web Worker. В первом случае обработка событий и обновление обоих индикаторов приостанавливаются на время вычислений. Во втором случае вычисления выполняются в отдельном потоке. Для каждой пары используется заранее заданная длина входной строки.

4. Анализ уязвимости регулярного выражения

Анализ выполняется библиотекой recheck в браузере. Результат включает оценку сложности и, при обнаружении уязвимости, описание входной строки, вызывающей избыточный перебор. Неопределённый результат анализа не подтверждает отсутствие уязвимости.

Набор экспериментов включает 11 пар выражений. Методика предусматривает выполнение одинаковых проверок в Node.js, Chromium и Chromium внутри Docker с ограничением вычислительных ресурсов.     6. Способы снижения риска ReDoS

    • Устранение неоднозначного разбиения строки: вложенных повторов (a+)+ и пересекающихся альтернатив (a|aa)+.
    • Использование обязательных разделителей между повторяющимися частями выражения, если это соответствует проверяемому формату.
    • Проверка производительности на строках, не соответствующих выражению, в том числе при несовпадении последнего символа.
    • Ограничение длины входных данных и времени выполнения. Для принудительного прерывания синхронной проверки требуется отдельный воркер; setTimeout в том же потоке не прерывает вычисление.
    • Применение анализаторов сложности, например recheck, и движков без backtracking, например RE2, с учётом поддерживаемого синтаксиса.

    Источники и примечания

    1. Stack Overflow, 20 июля 2016 года. Обработка публикации, содержащей около 20 000 последовательных пробелов, привела к длительному выполнению выражения ^[\s\u200c]+|[\s\u200c]+$. Задержки ответа главной страницы вызвали ошибки проверки доступности серверов и их исключение из балансировки нагрузки. В данном случае сложность обработки была квадратичной, O(n²). Впоследствии регулярное выражение заменили обработкой через substring. Постмортем. ↑
    2. Cloudflare, 2 июля 2019 года. Правило WAF Managed Rules содержало фрагмент .*(?:.*=.*). После развёртывания правила загрузка процессоров, обслуживающих HTTP/HTTPS, приблизилась к 100%. Инцидент сопровождался ошибками HTTP 502 и снижением доступности сервиса. Разбор в блоге Cloudflare. ↑
    3. OWASP: Regular expression Denial of Service — описание ReDoS и характерных уязвимых конструкций.
    4. recheck — документация детектора, который используется в разделе 4.
    regex-bench — экспериментальный стенд для лабораторной работы. Результаты измерений зависят от аппаратной платформы, версии движка и условий выполнения.
